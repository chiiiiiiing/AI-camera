# UI 交付清单调整计划（2026-07-21）

## 目标

基于队友补充的《给 UI 设计队友-交付清单》，把当前项目的“真实实现状态”和“仍待设计补充的内容”拆清楚，避免后续协作时出现以下问题：

- 已经实现的内容被误写成“未完成”
- 尚未实现的功能被误写成“已实现”
- UI 队友继续投入的资源方向不对
- 开发侧后续任务优先级不清晰

这份计划只做两类调整：

1. 校正文档，让团队对当前状态形成统一认知
2. 对仍需继续推进的内容给出明确的后续执行顺序

不在本轮凭空扩展新的大功能页。

---

## 一、我们要做什么

### 1. 校正文档中的实现状态

需要把队友补充文档里与当前工程不一致的描述逐项改正，包括但不限于：

- 冷启动流程
- 登录态与个人主页关系
- 第三方登录图标状态
- 输入框图标形式
- 相机顶部入口结构
- 设置页是否真正存在

### 2. 明确当前仍缺哪些设计资源

把“还需要 UI 继续提供的内容”从“功能没做”里剥离出来，单独列出，例如：

- 启动器图标
- 引导动画参考
- 登录页品牌强化素材
- 社区/个人页视觉定稿

### 3. 明确哪些是后续功能，不属于当前主线交付

例如：

- 忘记密码页
- 编辑资料页
- 完整设置页

这些内容不应该继续写成“当前已实现”，也不应该和主线相机交付混为一谈。

### 4. 让仓库内文档可以直接用于协作

需要把调整结果同步进：

- UI 交付清单校正版
- README
- 必要时同步到实施清单

---

## 二、怎么做调整

### 1. 先对齐“当前真实状态”

以当前工程源码、导航流、相机页、登录页和已有测试为准，不以旧文档描述为准。

优先检查：

- 启动页 → 相机页流转
- 未登录点击个人主页行为
- 人像两阶段引导
- 第三方登录图标
- 顶部模式入口

### 2. 把差异分类

对每一条差异，按以下三类处理：

- A 类：文档描述不准，但代码已经实现  
  → 直接修正文档

- B 类：文档提的是设计资源缺口，不需要立刻写代码  
  → 放入“待 UI 交付资源”

- C 类：文档暴露出真实代码缺口，且影响当前主流程  
  → 进入立即开发清单并补代码

### 3. 输出一份可直接发给协作者的清单

清单必须满足：

- 非开发同学也能快速看懂
- 明确“已实现 / 未实现 / 待设计 / 后续阶段”
- 不使用模糊措辞

### 4. 如果发现主流程代码仍有缺口，立即修复并验证

优先级顺序：

1. 冷启动流程
2. 个人主页登录态分流
3. 人像两阶段引导
4. 关键页面编译与测试

---

## 三、调整后我们接下来应该怎么推进

### 第一优先级：继续让 UI 补资源

最值得 UI 继续补的内容：

1. 启动器图标
2. 引导动画参考
3. 引导颜色定稿
4. 登录页品牌强化素材

原因：

- 这些东西会直接影响产品完成度
- 但不需要大改当前架构
- 开发接到资源后替换成本低

### 第二优先级：继续收口相机体验

开发侧后续最值得继续打磨的是：

1. 人像模式两阶段视觉细节
2. AI cue 到视觉引导的映射一致性
3. 引导完成态反馈节奏

### 第三优先级：后续功能页

在主线交付稳定之后再推进：

1. 忘记密码页
2. 编辑资料页
3. 完整设置页

---

## 四、本轮执行范围

本轮实际执行：

- 生成并维护 UI 交付清单校正版
- 在 README 中补充这份文档入口
- 同步说明当前产品流和边界

本轮不做：

- 凭空设计完整设置页
- 补全忘记密码业务流
- 扩写后端或账号系统

---

## 五、完成标准

当以下条件同时满足时，本轮调整完成：

- UI 交付清单的校正版已落地到项目文档
- README 能直接指向该文档
- 文档中对“当前实现状态”的描述与当前工程一致
- 文档中对“待设计资源”的划分清楚
- 关键代码主流程仍可编译通过
