# AI 引擎优化与验收（2026-10-10）

本轮按已确认的「中端 Android 优先、端侧离线」目标修改代码。保留 V9 static int8 模型和现有素材，未重新训练、替换线上模板库或发布 App。

## 当前真实架构

实际 Android 实现在 `app-arch/aicamera-app/`。主链路是相机 → 预处理 → V9 ONNX 512 维 embedding → top8 检索 → 场景/光线重排 → 模板稳定选择 → 几何引导。模型本身不预测手机应移动多少，也不直接输出姿势骨架。

`ai/engine/` 是另一套 C++ 引擎骨架和 portable index 实现，目前没有接入上述 Android 主链路；C++ 的改进不能算成手机端已获得的性能提升。根目录 `frontend/` 则保留较早的 UI 原型。

已读取提供的 Web 预览站页面源码，包含分析、旋转、俯仰、水平转向、主体移动、稳定验证、无主体等状态。飞书链接未能读取，暂无可用飞书连接，因此本轮不能声称已核对飞书完整需求。预览中的俯仰、偏航、全身姿势能力在当前 AI 实现中仍有缺口。

## 已实施的优化

| 方面 | 原问题 | 本轮行为 |
|---|---|---|
| 模型调度 | 每个被接收的分析帧都预处理和运行模型 | V9 每 500ms 最多采样一次，缓存基础推荐；几何引导继续逐处理帧更新 |
| 跨帧状态 | 热替换与主线程 reset 可能交错；镜头/朝向切换残留旧推荐 | 在推理线程统一 reset；镜头、旋转、暂停恢复和引擎替换使缓存失效 |
| 相机资源 | SharedFlow 没有接收者或取消时可能丢失 ImageProxy；暂停帧被直接忽略 | 单消费者 Channel 交接并回收未交付帧；停止状态由调度器关闭帧 |
| 人脸检测 | 超时不取消 ML Kit 任务，却已回收其 Bitmap；重复失败沿用旧框 | 等任务完成才回收 Bitmap；限制一个在途任务；失败清空主体结果 |
| 构图反馈 | 模板相似度被当成完成度；缺人物但手机端平仍可能完成 | 几何信号验证进度；必需主体缺失时进度为零；不展示虚构主体框 |
| 模板目标 | 未标注主体位置也被映射到左上三分点 | 显式位置才生成目标区，`none`/未知值不编造位置 |
| 推荐稳定 | 低 margin 或现任移出候选时，内部状态与实际返回值不一致 | 独立稳定器，候选连续领先才切换；新场景正确更新现任；空结果清状态 |
| 数值可靠性 | 大数累加溢出、非有限值或零向量影响排序 | 防御性归一化、double 累加、无效输入拒绝和余弦边界保护 |
| 引擎生命周期 | 复制失败可能卡在 COPYING；关闭后后台任务又发布 READY | 复制/校验/加载进入完整异常边界；发布与关闭共享同步机制；失败释放会话 |
| 模型契约 | ONNX 张量签名和索引结构校验不充分 | 检查实际输入/输出类型及形状、维度和向量有效性；验证资产版本 |
| 性能观测 | 只看平均值，缓存更新可能稀释模型耗时 | 单独统计模型采样 FPS、模型+检索 p50/p90 和几何耗时 |
| C++ 检索 | 为 top-k 全量排序并分配所有候选 | 有界堆，排序部分 O(N log K)、临时空间 O(K)，保持确定性排序 |
| 数据与交付 | 旧缓存可被改写为新模型身份；历史质量数字直接放行 | 校验模型/图片/预处理/向量 hash；重算打包索引的检索指标；检查键序和归一化 |
| 训练切分 | 重复图片或不同 teacher 空间可能进入同批数据 | 拒绝重复 ID/hash/path、混合 teacher 空间和异常向量，通过后才写产物 |
| 持续验证 | 缺 Catch2 时 C++ CI 没有可执行测试 | 基础回归不依赖 Catch2；CI 使用 CTest，并增加数据契约回归 |

`minInferenceIntervalMs=500` 是当前中端机默认值，尚未实现按温度自动调节或基于画面变化提前触发。几何帧率取决于设备实际吞吐，不等于保证 30fps。

## 质量数字应如何理解

重新计算打包的 728 条 V9 int8 embedding，库内 leave-one-out top5 同场景命中率为 **96.15%**。每条模板查询时排除自身，但这些图片本身属于已有的 train 579 / val 71 / test 78 数据集合。它是索引一致性诊断，不是独立新照片泛化准确率，也不是“构图建议正确率”。本轮没有证据宣称模型精度提高。

现有 728 条 embedding 没有生成模型 SHA-256 血缘字段。校验器能确认模型文件 hash、索引结构和实际检索指标，但不能反向证明旧向量一定由当前模型生成。新生成流程记录血缘；旧产物保持不变，需在计划好的重建批次中补齐。

## 本地验证

- C++：g++ 15.2、C++17、O2、Wall/Wextra/Wpedantic 编译零告警；极值/损坏索引/API/8 线程只读状态回归通过。真实 104 条旧正式模板全部自检，并逐条将 top5 与独立全排序计算比较通过。
- Android 纯逻辑：去重后 **101 项 JUnit 通过**（采样/构图几何/状态机 38 项，V9/资产/场景估计/滤镜/变焦/调度指标等 63 项）。最终把真实 FramePipeline、FramePreprocessor、GeometryGuidanceStage、FaceSubjectDetector、V9 和引擎管理器共同编译，并复跑相关 41 项通过。使用本机 Kotlin/JUnit 编译执行；Android/ONNX/ML Kit 等外部接口使用临时测试桩，不能代替完整 APK 构建或真实设备测试。
- Python：可用依赖下 142 项，141 通过、1 项因缺 USearch 跳过。全量发现 146 项，另有 4 个测试模块因缺 torch/onnx 不能导入；没有把全量标为通过。
- 资产：实际 728 条打包索引重算通过，96.15% 与历史报告一致；明确报告旧模型血缘缺失。
- 完整 Android Gradle：本机启动阶段报 `Unable to establish loopback connection`，未进入完整构建；JBR/IPv4/禁 daemon 参数的尝试未解决。尚未生成或验证新 APK。
- 设备：ADB 未发现连接手机；没有手机端延迟、内存、温度、电量或拍摄效果结果。CMake 生成器/Android ABI 也未在本机验证。

## 接下来按这个顺序验收

### P0：中端真机闭环

先恢复 Android 构建并在一台首发中端机运行。覆盖冷启动、权限拒绝/恢复、前后摄往返、0/90/180/270 度旋转、前后台切换、人物进出、无人物、快速换场景、模型/索引损坏降级。

连续预览至少 30 分钟。分别记录 ONNX embedding、模型+检索、几何阶段和整个管线的 p50/p90、PSS、温度和电量变化。现有预算是 **ONNX embedding p50 ≤80ms、p90 ≤150ms**；新增 `inferenceP50Ms` / `inferenceP90Ms` 含检索与推荐，不能拿它们冒充 ONNX-only 延迟。`modelFps` 也与几何输出的 `effectiveFps` 不同。

`ai/tools/benchmark_android_v9_engine.sh` 可采集现有设备信息和内存证据；它不直接测出 embedding 延迟、温度或耗电百分比。验收时应补实际采样记录。

### P1：建立独立效果评估

固定一批未进入训练或模板库的查询照片/短视频，按拍摄会话、人物、地点和近重复图片分组隔离，冻结后再调阈值。当前只排除了精确重复，近重复/同人同地泄漏仍需专门处理。

分别报告：分场景 top1/top5、建议可执行率、方向错误率、无主体误引导率、每分钟模板切换次数、达标后误退出率、首次有效提示耗时。对 teacher、V9 FP32、V9 int8 用同一测试集比较；保留低光、逆光、多主体、遮挡、横竖屏等切片，不能只看总平均。

先补弱类和失败案例，再讨论换大模型。现有小模型、几百条索引适合继续 exact search；是否引入 ANN、增加模型宽度或新 runtime，应以手机实测和独立效果集为依据。

### P1：补足产品能力边界

目前可靠信号主要是 IMU 水平角与人脸框。人脸框不是全身姿态，场景分类不是机位三维几何。预览里的 PITCH/YAW、全身轮廓、多人站位，应先定义输入信号、置信度、坐标系和降级行为，再接对应检测/姿态模块。不要依据单张模板文本硬编物理移动方向。

非人像主体、预览裁剪与分析坐标映射、快速场景切换触发、热状态分级仍需专项验收。滤镜/自动变焦目前主要输出建议；是否实际控制渲染与 CameraX 应由 App 接入闭环确认。

### P2：可持续交付

新一轮模型重建时给模型、预处理配置、索引和 metadata 形成同一版本包，补齐 hash 血缘和独立评估报告。保留可回退旧版本，验证断电/复制失败后恢复。未来再把可解释的失败原因和无图像的端侧性能统计接入调试面板。

C++ 若计划成为真正 Android runtime，还需补真实模型推理、严格 JSON 解析和包含 buffer 长度、YUV plane/stride 的输入 ABI；当前 API 不足以安全表达任意 CameraX YUV 帧。
