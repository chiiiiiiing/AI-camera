# 架构锚点 — 防止迭代漂移

> **写作目的**：经过多轮"找不足→修复→再找不足"的迭代后，需要一份文档锁定已确认的关键架构决策。
> **后续任何人（包括 AI）做修改时，以下决定不应再被推翻，除非有明确的新需求驱动。**

---

## 不可推翻的架构决策

### 1. 相机层：CameraX + PreviewView（不可换）

```
决策：CameraX 1.4+ → PreviewView → ImageAnalysis (YUV_420_888, STRATEGY_KEEP_ONLY_LATEST)
理由：Google 官方推荐，封装 Camera2 复杂性。替换为 Camera2 裸写不会带来显著收益。
锁定：不要因为"性能优化"把 CameraX 换成 Camera2 裸写。
```

### 2. 推理层：IInference 接口 + LiteRT（可替换接口，暂不可换框架）

```
决策：所有推理通过 IInference.predict(ByteBuffer, PreprocessedFrame) → Any? 接口
理由：队友模型到位后只需新增实现类，管线其余代码不动。
锁定：不要改变 IInference 的接口签名。不要同时接入 3 个推理框架。
```

### 3. UI 层：Compose + AndroidView 混合（不可推翻）

```
决策：
- 相机预览 + 旧对焦 Overlay → AndroidView (CameraX 要求)
- 引导 Overlay → Compose Canvas (队友设计系统)
- 控件层 → Compose (Material3)

理由：这是 CameraX + 设计规范的必然结果。尝试全 Compose 或全 View 都会有不可克服的问题。
锁定：不要试图消除 AndroidView。两套系统的并存是刻意的架构选择。
```

### 4. 引导系统：GuidanceStateMachine + 14 Cue × 5 视觉家族（不可推翻）

```
决策：使用队友设计的 14 种 GuidanceCue + 5 个 GuidancePhase + 5 个 GuideVisualFamily。
理由：来自队友 Figma 设计 + 产品需求。视觉家族作为模型输出和渲染之间的唯一桥梁。
锁定：不要重新发明一套不同的引导分类体系。不要绕过 GuidanceStateMachine 直接改 Canvas。
```

### 5. 状态管理：ViewModel + StateFlow（不可推翻）

```
决策：MVVM 架构。CameraViewModel / PipelineViewModel / RenderViewModel 各司其职。
理由：Hilt 已集成，Compose collectAsStateWithLifecycle 天然匹配。
锁定：不要引入 Redux/MVI 库。不要跨 ViewModel 直接访问其他 ViewModel 的状态。
```

### 6. 设置系统：SettingsState data class（不可推翻）

```
决策：所有设置项通过单一 SettingsState data class 传递，源头在 AppNavGraph 中 remember。
理由：已验证用 10 个独立 Boolean/Float 参数会导致函数签名爆炸。
锁定：新增设置项只在 SettingsState 中加字段，不再新增独立参数。
```

### 7. 认证系统：AuthRepository 接口 + SharedPreferences 实现（接口稳定，实现可换）

```
决策：AuthRepository 提供 register/login/logout/isLoggedIn 接口。
理由：MVP 用本地存储，后续可无缝切到服务端 API。
锁定：不要改变 AuthRepository 的公开 API 签名。后续只新增实现类。
```

### 8. 相机手势：GestureDetector + ScaleGestureDetector（不可推翻）

```
决策：使用 Android 原生手势识别器，单击对焦 + 双指变焦 + 长按锁定。
理由：手写状态机方案已废弃。
锁定：不要回到手写 ACTION_DOWN/MOVE/UP 状态机的方式。
```

## 允许演化的部分

| 区域 | 允许改什么 | 不允许改什么 |
|------|-----------|-------------|
| 引导渲染 | 颜色值、动画参数、新视觉修饰 | GuidanceCue 枚举、视觉家族映射逻辑 |
| 主题系统 | Color.kt 中的色值 | 颜色令牌的名称 |
| 社区页 | Feed 卡片样式、数据结构 | 不要接真实后端（MVP 阶段） |
| 设置页 | 新增设置项 | SettingsState 的传递方式 |
| 性能优化 | 预处理算法、推理线程数、Buffer 池 | IInference 接口 |
| 认证 | 新增 AuthRepository 实现类 | 公开 API 方法签名 |

---

## 防止"梯度爆炸"的检查清单

每次迭代完成后，对照此清单检查：

- [ ] ViewModel 是否仍然只有 3 个？（多一个就需要解释为什么）
- [ ] 是否有超过 5 个 Composable 参数的函数？（如果是，考虑是否该合并为 data class）
- [ ] 是否新增了第三方库？（每个新库都需要明确收益 > 维护成本）
- [ ] GuidanceCue 枚举是否仍为 14 个？（新增 cue 需要队友确认产品需求）
- [ ] AppNavGraph 路由是否仍 ≤ 7 个？（splash/login/register/main/settings/gallery + 1 预留）
- [ ] 是否有代码在绕开 GuidanceStateMachine 直接操作 Canvas？
- [ ] 是否有代码在绕开 IInference 接口直接调用具体的推理实现？
