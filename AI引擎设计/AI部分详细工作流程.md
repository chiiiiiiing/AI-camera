## 阶段 1：环境搭建（第 1-2 周）

### 目的

把整个工程骨架搭好，确保 C++ 代码能交叉编译出 Android `.so`，单元测试能跑，CI 能自动检查。这一步不写业务逻辑，只验证"工具链是通的"。

### 要做的事

1. **创建 Android 项目**
   - 用 Android Studio 创建 Kotlin 空项目，minSdk 29
   - 创建 `engine/` 子目录（C++ 源码目录）
   - 创建 `tools/` 子目录（Python 脚本目录）

2. **配置 CMake 构建**
   - C++17 标准，Android NDK 26+ 交叉编译
   - 集成三个 header-only 三方库：Eigen（线性代数）、nlohmann/json（JSON解析）、usearch（向量检索）
   - 集成 Catch2 测试框架
   - 产出 `libai_photo_engine.so`

3. **编译验证**
   - macOS 本地编译通过（先不涉及 NDK，纯验证 C++ 语法）
   - Android arm64-v8a 交叉编译通过
   - 写一个占位的 `engine.h` + `engine.cpp`，只返回版本号
   - 跑通第一个单元测试（验证编译和链接）

4. **配置 CI**
   - GitHub Actions：push 时自动编译 + 跑测试

5. **Python 工具链**
   - 创建虚拟环境，安装 PyTorch、OpenCV、MediaPipe、Ultralytics、Transformers、OpenAI SDK
   - 验证 4 个模型（MobileCLIP、YOLOv8-Pose、MediaPipe Seg、SmolLM2）都能在 Python 中加载并成功推理
   - 编写模型下载脚本

### 验收

- macOS 和 Android 都能编译出 `.so`
- 单元测试框架跑通
- CI 绿灯
- 四个模型在 Python 环境加载成功

### 给 AI 的提示要点

> "帮我配置一个 Android NDK + CMake 的 C++17 工程，集成 Eigen、nlohmann/json、usearch 三个 header-only 库，用 Catch2 做测试框架，产出一个 .so 动态库。同时写一个占位的 engine.h 和对应的单元测试。"

## 阶段 2：模板库构建（第 3-5 周）

### 目的

这是整个项目最重要的数据基础。构建 5,000-7,000 张高质量摄影模板，覆盖**人像、风景、静物**三大类。人像模板包含骨骼关键点+姿势信息，风景和静物模板则侧重构图+光线。后续 AI 引擎的所有"智能"都来自这个模板库——模板越好，引导越准。

### 要做的事

1. **收集照片（第 3 周）**
   - 优先使用自行拍摄、明确书面授权素材，以及 Openverse 检索的 CC0/PDM 候选照片
   - Unsplash/Pexels 普通 API 不用于本项目的批量 AI 数据收集，除非平台另行书面授权
   - 按三大类搜索：人像（海滩、街拍、室内、合影等）、风景（山川、海岸、城市天际线、日落等）、静物（美食、花卉、桌面摆件等）
   - 目标下载 7,000+ 张，人工筛选后保留 5,000-7,000 张
   - 筛选标准：授权可追溯、构图好看、分辨率够、不过度后期；人像还需复核肖像权

2. **CV 预处理（第 4 周）**
   - 对每张照片先跑 YOLOv8-Pose 检测是否有人
   - **有人**：跑 MediaPipe 分割 → 人像置黑 → MobileCLIP 提取纯背景向量 + 保存骨骼关键点
   - **无人（风景/静物）**：跳过分割和骨骼 → MobileCLIP 直接提取全帧向量
   - 输出每张照片的预处理 JSON（关键点可选 + embedding + mask 可选）
   - 处理异常：多人场景选最大目标、分辨率异常跳过

3. **LLM 美学标注（第 5 周）**
   - 用 GPT-4o-mini 的 Vision API 对每张照片做结构化分析
   - Prompt 要求输出严格 JSON：场景类别、灯光方向/角度、构图方式、相机角度估计、姿势描述、美学评分、拍摄建议
   - 费用极低（~$2-3 全量），速度很快（8 并发约 20 分钟）
   - 先用 10 张测试 Prompt 效果，调好后再全量跑
   - 质量校验：Schema 完整性检查 + 数值范围检查 + 失败照片用更强模型重标

4. **构建索引**
   - 将所有模板的 embedding 写入 USearch 向量索引（~5MB）
   - 模板元数据写入 JSONL 文件（~3MB）
   - 自检索验证：每张模板搜自己，Top-1 必须是自己

5. **人工抽检**
   - 每类场景随机抽 20 张（共 200 张）
   - 逐张检查场景分类、构图分析、角度估计是否合理
   - 通过率 > 90% 合格

### 验收

- 模板库 ≥ 3,000 张，覆盖 10 类场景
- 每张模板的 JSON 字段完整
- USearch 自检索通过
- 人工抽检通过率 > 90%
- 产出 `templates.idx` + `templates_meta.jsonl`

### 给 AI 的提示要点

> "帮我写一个 Python 脚本，从已授权来源或 Openverse 的 CC0/PDM 内容中收集照片，并完整保存授权证据。再写一个预处理脚本，对每张照片用 YOLOv8-Pose 提取骨骼点、用 MediaPipe Selfie Segmentation 做人物分割、用 MobileCLIP 提取背景图的 256 维 embedding。再写一个脚本，调用视觉模型对每张照片做结构化美学分析，最后构建 USearch 向量索引。"

## 阶段 3：模型量化（第 6-8 周）

### 目的

把 4 个模型从 FP32/FP16 压缩到 INT8/Q4 精度，控制总体积在 ~227MB（标准模式），同时确保精度退化在可接受范围内。在 C++ 侧封装统一的推理接口。

### 要做的事

1. **三个视觉模型 INT8 量化（第 6 周）**
   - MobileCLIP-S0 → INT8，目标 ~15MB，验证量化前后 embedding 余弦相似度 > 0.97
   - YOLOv8-Pose Nano → INT8，目标 ~4MB，验证关键点精度退化 < 2%
   - MediaPipe Selfie Segmentation 已有预训练小模型，直接使用（~200KB）
   - 准备校准数据集（从模板库随机抽 500 张）
   - 这三个模型都用 TFLite 格式，走 GPU/NNAPI 推理

2. **LLM 量化 + llama.cpp 集成（第 7 周）**
   - SmolLM2-360M → GGUF Q4_K_M，目标 ~200MB
   - 编译 llama.cpp 的 Android 版本（arm64-v8a）
   - 在 macOS 上先验证推理可用
   - Prompt 模板调优：准备 100 组测试数据，人工评分，迭代 system prompt 直到平均 > 3.5 分

3. **C++ 推理封装（第 8 周）**
   - 封装 `TFLiteRunner`：统一加载/推理 TFLite 模型，支持 CPU/GPU/NNAPI backend 切换
   - 封装 `CLIPEncoder`、`PoseDetector`、`SelfieSegmenter`：三个模型各自的专用接口
   - 封装 `LlamaRunner`：llama.cpp 的 C++ 包装，支持同步/异步生成、取消推理
   - 写集成测试：一张图输入，同时跑三个模型，验证输出合理性

### 验收

- 4 个模型全部量化到目标体积
- TFLite 三模型 C++ 集成测试通过
- LlamaRunner 可在 macOS 上生成中文建议
- Prompt 模板评分 > 3.5

### 给 AI 的提示要点

> "把 MobileCLIP-S0 和 YOLOv8-Pose Nano 从 FP32 量化到 TFLite INT8，校准数据集用模板库中的 500 张照片。把 SmolLM2-360M 转成 GGUF Q4_K_M 格式。编译 llama.cpp 的 Android arm64-v8a 版本。为这三个 TFLite 模型和 llama.cpp 分别写 C++ 封装类，用 PIMPL 模式隐藏实现细节。写集成测试验证全线推理通过。"

## 阶段 4：C++ 核心管线（第 9-13 周）

### 目的

这是整个项目最核心的阶段。实现 `engine_process_frame()`——输入一帧 YUV 图像 + IMU 数据，输出完整的视觉引导数据（箭头、构图线、文字建议；有人时额外输出虚线人形和姿势引导）。跑通从相机帧到 GuidanceOutput 的全链路。**先检测画面中有没有人，再决定走哪条引导路径。**

### 要做的事

1. **帧预处理（第 9 周）**
   - NV21 YUV → RGB 转换（用 NEON SIMD 加速，目标是 1080p < 2ms）
   - 帧缩放到各模型需要的分辨率（YOLO 640×640，CLIP/Seg 256×256）
   - 旋转处理（适配 Camera2 的 sensor orientation）
   - 前置摄像头镜像处理

2. **推理管线组装（第 10 周）**
   - 实现 `engine_process_frame()` 的完整流程：
     - 帧预处理 → 姿态估计 + 人像分割（并行）→ 骨骼归一化 → 差值计算 → 视觉引导生成
   - 实现引擎生命周期：`engine_init`（加载模型 + 模板库 + 预热）、`engine_shutdown`
   - 多线程模型：内圈线程（逐帧，高优先级）、外圈线程（场景切换时触发）、LLM 线程（每 1-3s）
   - 跨线程状态共享用 `std::atomic`，帧数据用无锁 Ring Buffer

3. **场景检索模块 / 外圈（第 11 周）**
   - 场景变化检测：连续 10 帧的 embedding 与当前模板余弦相似度 < 0.7 → 触发重新检索
   - USearch ANN 检索 top-3 模板
   - 选择最佳模板（考虑多样性，不总是选同一个）
   - 原子更新 TargetVector（内圈下次读取时自动切换）

4. **差值计算引擎（第 12 周）**
   - 骨骼归一化：Root-centered Scaling（以左肩→右髋为基准单位长度）
   - 关节夹角计算：肘、膝、肩、髋、脊柱倾斜、头部倾斜
   - 差值求解：当前关节夹角 vs 模板关节夹角、当前 IMU 角度 vs 模板相机角度、当前主体位置 vs 模板构图位置

5. **视觉引导生成（第 13 周）**
   - 箭头生成：根据 Δ 数值生成平移/旋转/俯仰箭头，包含位置、方向、类型、强度
   - 虚线人形：输出目标姿势的 17 个归一化关键点 + 颜色提示（绿/黄/红）
   - 构图辅助线：九宫格、地平线、主体区域框
   - 规则引擎：将 Δ 数值映射为中文语义槽位（如"相机抬高""左臂弯一些"）

### 验收

- `engine_process_frame()` 全链路跑通
- 内圈单帧延迟 < 20ms（macOS 本地）
- 外圈场景切换正确触发
- 所有引导数据（箭头、人形、构图线、文字槽位）正确生成
- 连续运行 5 分钟无 crash 无泄漏
- 单元测试覆盖率 > 60%

**这是最重要的里程碑。此时你有了一个功能完整的 AI 引擎。**

### 给 AI 的提示要点

> "实现 AI 摄影引擎的核心函数 engine_process_frame()。输入是 NV21 YUV 帧 + IMU 传感器数据，输出是 GuidanceOutput 结构体（引导箭头、虚线人形关键点、构图辅助线、文字建议）。引擎采用双圈异步架构：内圈逐帧跑姿态估计+差值计算(<20ms)，外圈在场景切换时做 CLIP 向量检索更新模板。多线程模型：内圈高优+外圈低优+LLM 最低优，跨线程状态用 atomic + 无锁 Ring Buffer。骨骼用 Root-centered Scaling 归一化后做关节夹角比对(±10°容差)。差值结果由规则引擎映射为中文语义槽位。"

## 阶段 5：差值计算与规则引擎完善（第 14-16 周）

### 目的

核心管线跑通了，但这阶段的引导质量可能还比较"粗糙"。这三周专门打磨——处理各种边缘 case，优化引导的合理性和用户体验。

### 要做的事

1. **骨骼归一化精度优化（第 14 周）**
   - 处理关键点检测失败的 fallback（部分遮挡、侧身、蹲姿）
   - 多人场景的主目标选择策略（选面积最大的还是最近的）
   - 前置摄像头镜像处理验证（确保引导方向正确）

2. **构图规则细化（第 15 周）**
   - 不同场景类别用不同的构图优先级（海滩优先对齐水平线、城市优先利用引导线、室内优先窗光方向）
   - 曝光建议：基于 Y 平面的平均亮度判断是否需要调整
   - 多人合影的排列规则（弧形排列、高度错落）

3. **人工评测（第 16 周）**
   - 准备 50 组测试场景
   - 人工判断引导是否"合理、有用"
   - 记录 bad case，调整规则阈值

### 验收

- 多种体型/姿势下归一化正确
- 引导方向与直觉一致
- 50 组评测"有用"率 > 80%

## 阶段 6：LLM 集成与语义翻译（第 17-19 周）

### 目的

把 SmolLM2 真正在 Android 真机上跑起来，实现从"语义槽位"到"自然语言建议"的翻译。同时做好 Fallback 方案——LLM 不可用时用模板引擎兜底。

### 要做的事

1. **真机调试（第 17 周）**
   - Android 真机上跑通 SmolLM2 推理
   - 测量延迟和内存（目标：骁龙 8 Gen 2 上 20 token < 500ms，额外内存 < 300MB）

2. **LLM 调度器（第 18 周）**
   - 触发策略：语义槽位内容变化 + 距上次生成 ≥ 1s
   - 取消策略：新的 Δ 到达时取消旧的推理
   - 结果缓存：相同槽位不重复生成

3. **Fallback 模板引擎（第 19 周）**
   - 编写 200+ 句预定义模板，按场景类别 + Δ 类型索引
   - 用于 LLM 加载失败、超时、极简模式等场景
   - 与 LLM 生成结果对比评测

### 验收

- LLM 真机推理 < 500ms
- 文本建议人工评分 > 3.5/5
- Fallback 引擎可独立工作且语句通顺

## 阶段 7：JNI 接口封装（第 20-21 周）

### 目的

把 C++ 引擎包装为 App 团队可以直接调用的 Kotlin 接口，交付正式的 `.so` 库。

### 要做的事

1. **JNI 实现（第 20 周）**
   - 实现 `engine_jni.cpp`：所有 engine.h 中声明的 C 函数 → JNI 包装
   - YUV 帧用 `DirectByteBuffer` 零拷贝传递
   - C struct ↔ Java object 的字段映射

2. **Kotlin Wrapper（第 21 周）**
   - 编写 `AIPhotographyEngine.kt`（App 团队直接用的接口）
   - 协程封装 LLM 异步结果
   - 编写 Demo App：Camera2 取景 → AI 引擎 → Canvas 渲染引导

3. **交付物**
   - `libai_photo_engine.so`（arm64-v8a）
   - `engine.h`（C 头文件）
   - Kotlin Wrapper 源码
   - 模型文件包
   - 集成文档

### 验收

- Demo App 在真机上显示 AI 引导
- JNI 层无内存泄漏

## 阶段 8：性能调优与真机测试（第 22-25 周）

### 目的

从"能用"到"好用"——在 5 台不同档次的 Android 设备上达到性能目标，解决发热、掉帧、内存问题。

### 性能目标

| 指标 | 目标值 |
|---|---|
| 内圈单帧延迟（P50） | < 15ms |
| 内圈单帧延迟（P99） | < 25ms |
| UI 渲染帧率 | 30fps 稳定 |
| 内存占用（运行时） | < 500MB |
| 冷启动时间 | < 3s |
| 连续使用 10 分钟电量 | < 8% |

### 要做的事

1. **Profiling（第 22 周）**
   - 用 Android GPU Profiler + Simpleperf 定位瓶颈
   - 重点看：YUV 转换、模型推理、JNI 边界

2. **优化（第 23 周）**
   - NEON SIMD 手写关键循环
   - 帧 buffer 池化减少分配
   - 热感知降档策略（根据设备温度自动降帧率/降模型档位）

3. **多设备测试（第 24-25 周）**
   - 5 台设备矩阵：SD 8 Gen 3（高端）→ SD 4 Gen 1（低端）
   - 30 分钟压力测试
   - Bug 修复

### 验收

- 5 台设备均达性能目标
- 30 分钟连续运行无 crash、无 ANR
- 内存无持续增长趋势

## 与 App 团队的协作

| 你的阶段 | 你交付给 App 团队 | 他们开始做什么 |
|---|---|---|
| 阶段 1 结束 | `engine.h` 初稿 + mock `.so` | 搭建 Camera2 + Canvas 框架 |
| 阶段 3 结束 | 最终版 `engine.h` + 数据结构文档 | 实现 GuidanceOverlayView 渲染 |
| 阶段 4 结束 | 可用的 `.so` + Demo App | 集成测试 |
| 阶段 7 结束 | 正式 v1.0 `.so` + 全部文档 | 最终集成 |

**关键原则**: 每两周和 App 团队同步一次接口变更。在提供真 `.so` 之前，先给 mock 数据让他们能并行开发。
