# 团队协作与 GitHub 工作流

> 本文档说明：如何用 Git 管理这个项目，以及你（AI 引擎）和 App 团队如何高效协作。

---

## 一、Git 分支策略

采用 **Trunk-Based Development**（主干开发），分支简洁，适合小团队。

```
main ─────────────────────────────────────────────────────►
  │                                                         
  ├── feature/engine-setup ──► merge (阶段 1 完成)           
  ├── feature/template-db ───► merge (阶段 2 完成)           
  ├── feature/model-quant ───► merge (阶段 3 完成)           
  ├── feature/core-pipeline ─► merge (阶段 4 完成)           
  └── ...
```

### 规则

| 规则 | 说明 |
|---|---|
| `main` 分支 | 始终保持可编译、测试全通过的状态 |
| 功能分支 | 每个阶段一个分支，命名: `feature/<阶段名>` |
| 不要直接 push main | 所有改动通过 PR 合并 |
| 每阶段结束后合并 | 不要长期维护未合并的分支 |

### 实际操作

```bash
# 初始化仓库（如果还没做）
cd /Volumes/桌面/AI-camera
git init
git add .
git commit -m "初始提交: 项目文档 + 阶段1环境搭建"

# 开始一个新阶段
git checkout -b feature/template-db
# ... 开发 ...
git add .
git commit -m "完成照片收集脚本"
# ... 继续开发 ...
git commit -m "完成CV预处理管线"
# 阶段完成后
git checkout main
git merge feature/template-db
git push origin main
```

## 二、Commit 规范

用中文写 commit message，格式：

```
<类型>: <简短描述>

<详细说明（可选）>
```

### 类型前缀

| 前缀 | 用途 | 示例 |
|---|---|---|
| `feat:` | 新功能 | `feat: 实现 NV21→RGB 转换` |
| `fix:` | 修 bug | `fix: 前置摄像头镜像方向错误` |
| `refactor:` | 重构（不改功能） | `refactor: 用 NEON SIMD 重写色彩转换` |
| `test:` | 新增或修改测试 | `test: 添加多人场景关键点选择测试` |
| `docs:` | 文档变更 | `docs: 更新接口文档, 添加 CameraTarget` |
| `chore:` | 工程配置 | `chore: 升级 CMake 最低版本到 3.22` |
| `perf:` | 性能优化 | `perf: YOLO 推理改为 NNAPI delegate` |

### 示例

```
feat: 实现相机目标点生成逻辑

根据模板的 subject_placement 计算 CameraTarget 位置。
offset_magnitude 用于驱动 UI 呼吸动画强度。
```

## 四、与 App 团队的分工

```
┌─────────────────────────────────────────────────┐
│                   Git 仓库                        │
│                                                  │
│  engine/           ← 你维护                      │
│  tools/            ← 你维护                      │
│  docs/             ← 共同维护                     │
│  app/              ← App 团队维护                 │
│                                                  │
└─────────────────────────────────────────────────┘
```

### 你的交付物（给 App 团队）

| 阶段 | 交付内容 | 形式 |
|---|---|---|
| 阶段 1 完成 | `engine.h` 头文件 + mock `.so` | 提交到仓库 `engine/include/` |
| 阶段 3 完成 | 最终版 `engine.h` + 数据格式文档 | 提交 + 文档说明 |
| 阶段 7 完成 | 正式 `libai_photo_engine.so` + Kotlin Wrapper | 提交 + Demo App |

### App 团队的交付物（给你）

| 他们做什么 | 你需要什么 |
|---|---|
| Camera2 帧采集 | YUV 帧的 `DirectByteBuffer` 格式确认 |
| IMU 传感器读取 | pitch/roll/yaw 的坐标系方向确认 |
| Canvas 引导渲染 | 各引导元素的视觉反馈 → 你据此调整参数 |

## 五、接口变更流程

当你需要修改 `engine.h` 时：

```
1. 先在 engine/include/engine.h 修改接口
2. 同步更新 engine/src/core/engine.cpp 骨架实现
3. 同步更新 engine/tests/ 中的测试
4. 编译 + 跑测试确认通过
5. 更新 技术设计与工作流程.md 中第五章（接口定义）
6. Commit 时在 message 写明接口变更:
   "feat: GuidanceOutput 新增 camera_target 字段，替代旋转箭头"
7. 通知 App 团队（发消息/更新工作进度.md）
```

**原则**: 接口变更必须同步更新文档，不能让文档落后于代码。

## 六、协作节奏

```
每两周一次同步:
  ├─ 你报告 AI 引擎进度
  ├─ App 团队报告 UI 进度
  ├─ 确认接口是否需要调整
  └─ 更新工作进度.md

里程碑:
  阶段 4 完成 (约第 13 周)
    → 双方第一次真正联调
    → App 团队用真实 .so 替代 mock 数据
```

### 沟通渠道建议

| 内容 | 方式 |
|---|---|
| 接口定义 | `engine.h` 本身就是协议，改动时在 commit message 说明 |
| 问题/Bug | GitHub Issues |
| 进度同步 | 更新 `工作进度.md`，每两周互相看一眼 |
| 紧急问题 | 直接发消息 |

## 七、GitHub Issues 使用规范

每个 Issue 用标签分类：

| 标签 | 颜色 | 用途 |
|---|---|---|
| `ai-engine` | 蓝色 | AI 引擎相关 |
| `app-ui` | 绿色 | App UI 相关 |
| `interface` | 红色 | 接口变更讨论 |
| `bug` | 红色 | Bug |
| `enhancement` | 黄色 | 功能增强 |

### Issue 模板示例

```markdown
**标题**: [ai-engine] process_frame 在多人场景下选择错误目标

**描述**:
画面中有 3 个人，引擎选了一个最远的做为主目标。
预期应该选最近（面积最大）的。

**复现**:
1. 打开相机对准 3 人合影场景
2. 观察 GuidanceOutput.pose 的关键点
3. 关键点定位在最远处的人身上

**环境**: 骁龙 8 Gen 2, Android 14
```

## 八、代码审查（Code Review）

即使只有两个人，PR 也应该互相看一眼：

### PR 检查清单

- [ ] 编译通过？
- [ ] 测试全过？
- [ ] 接口变更同步更新了文档？
- [ ] 没有遗留的调试代码（`printf`、`std::cout`）？
- [ ] 新增代码有对应测试？
- [ ] Commit message 清晰？

### PR 描述模板

```markdown
**变更内容**: 一句话说明改了什么

**影响范围**: engine/ app/ docs/

**测试**: 
- [ ] 本地编译通过
- [ ] 单元测试全过
- [ ] （如有）真机测试通过

**关联 Issue**: #123
```

## 九、AI 引擎 .so 的版本管理

每次交付给 App 团队时，更新版本号：

```
版本格式: <主版本>.<次版本>.<修订号>

0.1.0  — 阶段 1 骨架 (当前)
0.2.0  — 阶段 3 完成 (模型量化 + 推理框架)
0.3.0  — 阶段 4 完成 (全链路 process_frame)
0.4.0  — 阶段 7 完成 (JNI 封装, 可给 App 团队集成)
1.0.0  — 阶段 8 完成 (正式发布)
```

版本号写在 `engine/src/core/engine.cpp` 的 `engine_get_version()` 里，App 可以运行时获取。

```cpp
const char* engine_get_version(void) {
    return "0.1.0-dev";
}
```

## 十、快速上手：你的日常工作流

```bash
# 每天早上
cd /Volumes/桌面/AI-camera
git pull origin main              # 拉取最新代码（包括 App 团队的更新）
git checkout -b feature/xxx       # 新建今天的功能分支

# 开发中（用 Cursor/Claude Code 写代码）
# ... 改代码 ...

# 下班前
cd engine && cmake --build build  # 编译
./build/engine_tests              # 跑测试
cd /Volumes/桌面/AI-camera
git add .
git commit -m "feat: xxx"
git push origin feature/xxx

# 阶段完成时
# 在 GitHub 上创建 PR，请 App 团队同事 review
# 通过后 merge 到 main
```

---

> **最重要的原则**: `engine.h` 是你和 App 团队之间的合同。改了接口就要通知对方，改了文档就要同步代码。不要让任何一方基于过时的信息干活。
