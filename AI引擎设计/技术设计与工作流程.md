## 一、项目概述与目标

### 1.1 产品定位

一款纯端侧运行的 AI 智能摄影指导 App。用户打开相机对准拍摄对象，App 实时分析画面，以**相机目标点、姿势箭头、虚线人形、构图辅助线**等视觉元素叠加在取景器上，给出直观的拍摄建议。相机移动引导采用目标点方式——用户只需将画面中心对准目标点即可获得最佳构图。覆盖**人像、风景、静物**三大摄影类型：拍人时引导模特站哪、摆什么姿势；拍风景时引导构图和机位；拍静物时引导角度和光线。

### 1.2 目标用户

- 不会拍照的普通人（"拍照小白"）
- 希望拍出"朋友圈高赞照片"但缺乏摄影知识的用户
- 覆盖场景：人像（单人、情侣、合影）、风景（山川、海景、城市、日落）、静物（美食、花卉、小物件）

### 1.3 核心功能

| 功能 | 描述 |
|---|---|
| 场景识别 | 自动识别当前拍摄类型和场景（人像/风景/静物 → 子场景） |
| 构图指导 | 箭头引导用户移动相机位置/角度，叠加三分线/引导线（所有类型） |
| 姿势指导 | 虚线人形叠加在屏幕上，指引被摄者调整姿势（**仅人像时启用**） |
| 口语化建议 | 屏幕底部显示自然语言建议（如"往左走一步，相机放低一点"） |
| 实时反馈 | 30fps 逐帧更新引导，对齐后给出"完美"确认 |

## 二、系统核心架构设计

### 2.1 双圈层异步架构

```
         ┌──────────────────────────────────────────────────┐
         │                    外圈 (Outer Loop)               │
         │          触发频率: 场景切换时 (~0.1-0.5 Hz)         │
         │          单次耗时: 5-15ms                          │
         │                                                   │
         │   Camera Frame ──► MobileCLIP ──► Embedding(256d)  │
         │                         │                          │
         │                    Person Mask                      │
         │                   (MediaPipe)                      │
         │                         │                          │
         │              USearch ANN ──► 匹配模板               │
         │                         │                          │
         │              模板解析 ──► TargetVector              │
         │              (骨骼点 + 相机参数 + 构图规则)          │
         └─────────────────────────┬──────────────────────────┘
                                   │ 更新 TargetVector
                                   ▼
         ┌──────────────────────────────────────────────────┐
         │                    内圈 (Inner Loop)               │
         │          触发频率: 逐帧 (30 Hz)                     │
         │          单次耗时: <20ms                            │
         │                                                   │
         │   Camera Frame ──► YOLOv8-Pose ──► LiveSkeleton   │
         │   IMU Sensor  ──► 俯仰角/横滚角/偏航角             │
         │                         │                          │
         │              ┌──────────┴──────────┐              │
         │              │   差值计算引擎 (Δ)    │              │
         │              │  - 骨骼夹角差值       │              │
         │              │  - 构图比例差值       │              │
         │              │  - 相机角度差值       │              │
         │              └──────────┬──────────┘              │
         │                         │                          │
         │                   ┌─────┴─────┐                   │
         │                   │ 语义翻译层  │                   │
         │                   │ LLM/模板   │                   │
         │                   └─────┬─────┘                   │
         │                         │                          │
         │                   GuidanceOutput                   │
         │            (箭头 + 虚线人形 + 文字建议)             │
         └──────────────────────────────────────────────────┘
```

### 2.2 线程模型

```
线程 1 (主线程/UI 线程)
  ├── 接收相机帧回调 (Camera2 ImageReader)
  ├── 调用 AI 引擎 processFrame()  // 非阻塞，投递到工作线程
  ├── 接收 GuidanceOutput
  └── 驱动 Canvas/SurfaceView 渲染引导叠加层

线程 2 (AI 内圈推理线程 - 高优先级, 30fps)
  ├── YOLOv8-Pose 推理 (GPU/NPU)
  ├── 差值计算 (CPU, Eigen 向量运算)
  └── 输出 Δ 数据到 Ring Buffer

线程 3 (AI 外圈推理线程 - 低优先级, 按需触发)
  ├── 场景变化检测
  ├── MobileCLIP 推理
  ├── USearch 检索
  └── 更新 TargetVector → 写入原子共享变量

线程 4 (LLM 推理线程 - 最低优先级, 1-3s 间隔)
  ├── 从 Ring Buffer 读取最新 Δ
  ├── SmolLM2 推理
  └── 输出文本建议
```

**Ring Buffer 设计**:

- 内圈线程写入最新 `DeltaSnapshot`，LLM 线程读取
- 容量 3，写入不阻塞（覆盖最旧数据），读取不阻塞
- 所有跨线程共享状态使用 `std::atomic` 或 `folly::AtomicSharedPtr`

### 2.3 数据流时序

```
时间轴 ─────────────────────────────────────────────────────►

Frame:     F1    F2    F3    F4    F5   ...   F_N   F_N+1
           │     │     │     │     │           │     │
内圈:      ├─────┼─────┼─────┼─────┼─ ... ────┼─────┤  (30fps, 每帧)
           │ Pose │ Pose │ Pose │ Pose │       │ Pose │
           │ + Δ  │ + Δ  │ + Δ  │ + Δ  │       │ + Δ  │
           └──┬───┴──┬───┴──┬───┴──────┘       └──┬───┘
              │      │      │      ...              │
LLM:          └──────┴──────┴─ 每隔 1-3s 取最新Δ ───┘  (0.3-1 Hz)
                             │                    │
                             生成文本建议          更新建议

外圈:  ──────────────────────┬──────────────────┬──────► (按需)
                        场景切换检测          再次切换
                        Template Re-search
```

## 三、技术选型与关键决策

### 3.1 平台策略

| 决策项 | 选择 | 理由 |
|---|---|---|
| 目标平台 | **Android 优先** | 用户指定；Android 市场份额更大（尤其在新兴市场） |
| 最低 API Level | **Android 10 (API 29)** | 覆盖 95%+ 活跃设备；NNAPI 1.2 成熟可用 |
| 相机 API | **Camera2 API** | 比 CameraX 更底层，YUV 帧零拷贝访问；比 Camera1 支持更好的手动控制 |
| 传感器 | **SensorManager + 旋转矢量传感器** | 系统级传感器融合，比自行卡尔曼滤波更稳定 |

**为什么不选 Flutter/React Native 跨平台？**
AI 引擎需要 JNI 调用、NNAPI 硬件加速、YUV 帧直读——这些都需要平台原生能力。跨平台框架会引入额外的编解码开销和兼容性问题。后续 iOS 版本可以复用 90% 的 C++ AI 引擎代码，仅重写平台桥接层。

### 3.2 模型选型详细对比

#### 3.2.1 场景理解模型（Embedding）

| 候选模型 | 参数量 | INT8 体积 | 推理延迟(SD8G2) | 向量维度 | 结论 |
|---|---|---|---|---|---|
| MobileCLIP-S0 | 13M | ~15MB | 5ms | 256d | **✅ 首选** |
| CLIP-ViT-B/32 蒸馏版 | 88M | ~30MB | 15ms | 512d | 体积偏大 |
| MobileNetV3 + 自定义投影 | 5M | ~6MB | 3ms | 128d | 精度不足，需额外训练 |
| EfficientNet-B0 | 5.3M | ~6MB | 4ms | — | 无多模态对齐能力 |

**决策**: 选用 **MobileCLIP-S0**，INT8 量化后 ~15MB，256 维向量在 USearch 中检索速度 ~0.1ms（5000 条数据），与 CLIP 文本编码器对齐，方便后续用自然语言扩展模板检索。

#### 3.2.2 姿态估计模型

| 候选模型 | 参数量 | INT8 体积 | 推理延迟(SD8G2) | 关键点数 | 结论 |
|---|---|---|---|---|---|
| YOLOv8-Pose Nano | 3.3M | ~4MB | 6ms | 17 (COCO) | **✅ 首选** |
| MoveNet Lightning | 2.4M | ~3MB | 3ms | 17 | 精度略低，裁剪场景表现差 |
| MediaPipe Pose (Lite) | 4.2M | ~5MB | 5ms | 33 | 关键点过多，33 点对摄影建议冗余 |
| RTMPose-S | 5.6M | ~7MB | 8ms | 17 | 精度高但体积偏大 |

**决策**: 选用 **YOLOv8-Pose Nano**，17 个 COCO 关键点足够覆盖人体主要关节（肩、肘、腕、髋、膝、踝、眼、鼻）。与 YOLOv8 生态兼容，方便后续升级到更新的 YOLO 版本。

#### 3.2.3 人像分割模型

| 候选模型 | 参数量 | 体积 | 推理延迟 | 结论 |
|---|---|---|---|---|
| MediaPipe Selfie Segmentation | 200K | ~200KB | 1ms | **✅ 首选** |
| MobileSAM | 5.8M | ~6MB | 12ms | 体积大 30 倍，速度慢 10 倍 |
| SINet | 0.8M | ~3MB | 3ms | 中等选择 |
| DeepLabV3 (MobileNetV2) | 2.1M | ~8MB | 8ms | 精度高但过重 |

**决策**: 选用 **MediaPipe Selfie Segmentation**。本项目只需要知道"哪里是人"来对背景做 CLIP 向量提取，不需要像素级精确分割。200KB 的体积和 1ms 的延迟是三方案中最优的。

#### 3.2.4 端侧 LLM（文本生成）

| 候选模型 | 参数量 | Q4 体积 | 推理延迟(每 token) | 结论 |
|---|---|---|---|---|
| SmolLM2-360M | 360M | ~200MB | 15ms | **✅ 首选** |
| SmolLM2-135M | 135M | ~80MB | 8ms | 体积更小，可作为轻量模式 |
| Qwen2.5-0.5B | 500M | ~350MB | 25ms | 体积过大，能力溢出 |
| Gemma-2B (蒸馏) | 2B | ~1.2GB | 60ms | 太大，不适合移动端 |

**决策**: **标准模式用 SmolLM2-360M-Q4 (~200MB)**，轻量模式用 **SmolLM2-135M-Q4 (~80MB)** 或纯模板引擎。两种模式在 App 首次启动时根据设备可用 RAM 自动选择：
- RAM ≥ 6GB → 标准模式（LLM 生成）
- RAM < 6GB → 轻量模式（模板槽位填充）

SmolLM2-360M 生成 20-30 token 的摄影建议约需 300-450ms。由于文本建议不要求逐帧更新（1-3 秒更新一次即可），这个延迟完全可接受。

### 3.3 推理框架选择

| 模型 | 推理框架 | 硬件加速 | 说明 |
|---|---|---|---|
| MobileCLIP-S0 | TFLite (XNNPACK / GPU Delegate) | GPU / NPU | TFLite 对 CLIP 类模型支持成熟 |
| YOLOv8-Pose Nano | TFLite (NNAPI Delegate) | NPU (ANE 等价) | NNAPI 对卷积网络加速效果最好 |
| MediaPipe Selfie Segmentation | MediaPipe Tasks (TFLite 底层) | GPU | MediaPipe 自带 Android SDK，集成最简 |
| SmolLM2-360M | llama.cpp (JNI 编译) | CPU（ARM NEON 优化） | llama.cpp Android NDK 支持成熟 |
| USearch | 原生 C++ (header-only) | CPU | 无 GPU 加速需求，ANN 检索足够快 |

### 3.5 UI 引导渲染方案

AI 引擎输出数据，App 团队负责渲染。以下是各引导元素的渲染方式约定：

#### 3.5.1 相机目标点 (Camera Target)

相机移动引导采用目标点方式——画面显示一个发光圆点，用户将相机中心对准该点即可获得模板建议的构图。替代原来的旋转箭头方案，更直觉。

```
输出数据:
  - x, y: float             归一化屏幕坐标 [0-1]，目标点的位置
  - radius: float           目标点大小 (dp)，建议 24-48
  - offset_magnitude: float 目标点离画面中心的距离 [0-1]
                            0 = 已对准 (点在中心)
                            1 = 偏差最大 (点在边缘)
  - color_hint: enum        GREEN  (offset < 0.05, 已对准)
                            YELLOW (0.05 ≤ offset < 0.2, 接近)
                            RED    (offset ≥ 0.2, 偏差较大)
  - hint: string            "对准这里" / "往这移动"

渲染:
  App 在 Canvas 的 (x*w, y*h) 处绘制目标点
  - 外圈: 同心圆环, 2-3 层, 半透明
  - 中心: 实心小圆
  - 颜色: 按 color_hint  (绿/黄/红)
  - 光晕: offset_magnitude 越大光晕越明显 (呼吸动画)
  - 当 offset < 0.05 时, 目标点变为对勾✅或同心圆收缩动画表示"已对准"
```

**与原来箭头方案的区别**:
- 用户不需要理解"往左转"还是"往上抬"——只需要把相机中心对准目标点
- 目标点的位置由 AI 根据模板的最优构图计算出来
- 物理对应: 目标点在画面右下 → 用户需要把相机往右下移动（即对准它）

#### 3.5.2 姿势引导箭头 (Pose Arrow)

仅在**人像场景**使用，在画面中的身体关节位置显示箭头，提示被摄者调整姿势。

```
输出数据:
  - x, y: float             归一化坐标 [0-1], 关节在画面中的位置
  - direction: float        箭头指向 [0-360°], 示意关节应移动的方向
  - intensity: float        [0-1], 偏差越大越明显
  - label: string           "弯一些" / "抬高" / "放下" (短文本)

渲染:
  App 在关节位置绘制弧形小箭头
  alpha = 0.3 + 0.7 * intensity
  箭头方向 = direction
```

#### 3.5.3 虚线人形 (Dotted Figure Overlay)

```
输出数据:
  - keypoints: [(x,y) * 17]     17 个 COCO 关键点, 归一化坐标
  - connections: [(from, to)]   骨架连接对 (如 左肩→左肘)
  - opacity: float              整体透明度
  - colorHint: enum             GREEN(对齐好) / YELLOW(接近) / RED(偏差大)

渲染:
  App 绘制关键点圆圈 (半径 8dp)
  按 connections 绘制虚线 (strokeWidth 2dp, dashLength 6dp)
  颜色 = 按 colorHint (差 → 绿, 大 → 红)
```

#### 3.5.4 构图辅助线 (Composition Guides)

```
输出数据:
  - ruleOfThirds: bool          是否显示九宫格
  - horizonLine: float?         地平线 Y 坐标 [0-1]
  - subjectRegion: Rect?        主体建议区域 (归一化)
  - leadingLines: [(x1,y1,x2,y2)]  引导线

渲染:
  ruleOfThirds: 2 横线 + 2 竖线 (白色半透明)
  horizonLine: 水平虚线, 黄色
  subjectRegion: 矩形框线, 绿色
  leadingLines: 曲线/直线, 蓝色半透明
```

#### 3.5.5 文字建议

```
输出数据:
  - primaryText: string         主要建议 (1 行, <30 字)
  - secondaryText: string?      补充建议 (可选, 更详细)
  - confidence: float           LLM 生成置信度 [0-1]

渲染:
  App 在屏幕底部绘制半透明黑色背景 + 白色文字
  primaryText 字号 16sp, Bold
  secondaryText 字号 13sp, Regular
```

## 四、模型预算与分配方案

### 4.1 放弃 20MB 限制的论证

原文档提出"模型总体积须控制在 20MB 以内"。经分析，同时装载以下模型：

- 场景理解（CLIP 类）：~15MB INT8
- 姿态估计：~4MB INT8
- 人像分割：~0.2MB
- 端侧 LLM：~80-200MB Q4
- 向量数据库（模板索引）：~5-10MB

**物理上不可能在 20MB 内完成**。20MB 的约束可能源于对"端侧模型"的常见认知（对标 MobileNet 单模型场景），但不适用于多模型协同的复杂管线。

### 4.2 实际模型预算

| 组件 | 模型/数据 | 原始精度 | 量化后体积 | 加载位置 |
|---|---|---|---|---|
| 场景理解 | MobileCLIP-S0 | FP16 30MB | **INT8 15MB** | GPU/NPU |
| 姿态估计 | YOLOv8-Pose Nano | FP32 13MB | **INT8 4MB** | NPU |
| 人像分割 | MediaPipe Selfie Seg | FP32 0.8MB | **FP16 0.2MB** | GPU |
| 端侧 LLM | SmolLM2-360M | FP16 720MB | **Q4_K_M 200MB** | CPU (mmap) |
| 向量索引 | USearch (5000 条) | — | **~5MB** | CPU (mmap) |
| 模板元数据 | JSON 结构化数据 | — | **~3MB** | CPU |
| **合计** | | | **~227MB** | |

### 4.3 分档方案

| 模式 | LLM | 总模型体积 | 适用设备 | 文本建议质量 |
|---|---|---|---|---|
| **标准模式** | SmolLM2-360M Q4 (200MB) | ~227MB | RAM ≥ 6GB | 自然语言，丰富多变 |
| **轻量模式** | SmolLM2-135M Q4 (80MB) | ~107MB | RAM 4-6GB | 略简单，但仍为自然语言 |
| **极简模式** | 无 LLM（模板槽位填充） | ~27MB | RAM < 4GB | 固定句式 + 参数替换 |

App 首次启动时检测 `ActivityManager.MemoryInfo.totalMem`，自动选择合适的模式。

### 4.4 模型文件分发策略

```
方案 A (推荐): 基础 APK + 按需下载
  - APK 内仅包含极简模式的 27MB 模型（保底可用）
  - App 启动后根据设备能力提示下载标准/轻量模型包
  - 使用 Play Asset Delivery (PAD) 或自建 CDN

方案 B: 全部内置
  - APK 体积约 250MB
  - 对 Play Store 150MB 限制需使用 Android App Bundle (AAB)
  - 用户首次下载流量大，可能影响转化
```

**决策**: 采用方案 A，确保 APK < 50MB，模型文件通过 PAD 按需分发。

## 五、AI 引擎接口设计（供 App 团队对接）

### 5.1 设计原则

1. **纯 C 接口**: JNI 边界用纯 C 函数，内部 C++ 实现。避免 C++ 对象跨越 JNI 边界。
2. **无状态外泄**: 引擎内部状态完全封装，外部仅持有不透明句柄（`EngineHandle`）。
3. **零拷贝优先**: YUV 帧数据通过直接内存指针传递，避免 JNI 数组拷贝。
4. **线程安全**: 所有接口函数可被多线程并发调用（内部加锁或使用无锁结构）。

### 5.2 引擎句柄与生命周期

| 故障场景 | 降级行为 | 用户感知 |
|---|---|---|

| YOLOv8-Pose 加载失败 | **致命错误**，引擎不可用 | 提示用户设备不兼容 |

| 内存不足 (模型加载时) | 自动降级到更小模型档位 | 首次启动稍慢，之后正常 |

```python
# tools/build_template_db/preprocess.py
# 依赖: opencv-python, mediapipe, ultralytics, transformers, torch

from dataclasses import dataclass
from PIL import Image
import json

@dataclass
class PreprocessedPhoto:
    """单张照片的预处理结果"""
    photo_id: str
    file_path: str

    # 姿态关键点 (COCO 17点, 绝对像素坐标)
    keypoints_abs: list[dict]      # [{"x": 320, "y": 240, "conf": 0.95}, ...]

    # 人像分割 mask (二值, 同原图分辨率)
    mask_path: str                 # 保存为 PNG 文件

    # 背景图 (人像区域置黑)
    bg_only_path: str              # 保存为 JPEG

    # CLIP embedding (256d float32)
    embedding: list[float]

    # 图像元信息
    width: int
    height: int
    aspect_ratio: float

def preprocess_single(photo_path: str, output_dir: str) -> PreprocessedPhoto:
    """
    单张照片预处理:
    1. 加载图片
    2. YOLOv8-Pose 提取 17 个骨骼关键点
    3. MediaPipe Selfie Segmentation 生成人像 mask
    4. 将人像区域置黑, 保存背景图
    5. MobileCLIP-S0 提取背景图的 256d embedding
    6. 返回结构化数据
    """
    img = cv2.imread(photo_path)
    h, w = img.shape[:2]

    # Step 1: 姿态检测
    pose_results = yolo_pose_model(img)  # YOLOv8-Pose
    keypoints = pose_results[0].keypoints.xy.cpu().numpy()[0]  # 17x2

    # Step 2: 人像分割
    mask = selfie_segmenter.process(img)  # MediaPipe
    mask_binary = (mask > 0.5).astype(np.uint8) * 255

    # Step 3: 生成背景图 (人像区域置黑)
    bg_only = img.copy()
    bg_only[mask_binary > 0] = 0

    # Step 4: CLIP Embedding (从背景图提取)
    bg_pil = Image.fromarray(cv2.cvtColor(bg_only, cv2.COLOR_BGR2RGB))
    embedding = mobileclip.encode_image(clip_preprocess(bg_pil))
    # embedding shape: (256,) float32 numpy array

    # 保存中间产物
    mask_path = f"{output_dir}/{photo_id}_mask.png"
    bg_path = f"{output_dir}/{photo_id}_bg.jpg"
    cv2.imwrite(mask_path, mask_binary)
    cv2.imwrite(bg_path, bg_only)

    return PreprocessedPhoto(
        photo_id=photo_id,
        keypoints_abs=[{"x": k[0], "y": k[1]} for k in keypoints],
        mask_path=mask_path,
        bg_only_path=bg_path,
        embedding=embedding.tolist(),
        width=w, height=h,
        aspect_ratio=w/h,
    )
```

```python
"""
批量 LLM 标注脚本
依赖: openai (或 anthropic), pillow, tenacity
运行: python llm_annotate.py --input ./preprocessed/ --output ./annotated/ --api openai --model gpt-4o
费用估算: 5000 张 × ~800 input tokens × $2.50/1M + ~400 output tokens × $10/1M
        ≈ 5000 × ($0.002 + $0.004) ≈ $30 (使用 GPT-4o-mini 仅 ~$3)
"""

import os, json, time, argparse
from pathlib import Path
from concurrent.futures import ThreadPoolExecutor, as_completed
from tenacity import retry, stop_after_attempt, wait_exponential
import openai  # 或 from anthropic import Anthropic

# 配置
MAX_RETRIES = 3
CONCURRENCY = 8         # API 并发数 (注意 rate limit)
SAVE_INTERVAL = 100     # 每 100 张检查点保存

def build_annotation_prompt(preprocessed: dict) -> str:
    """构建发送给 LLM 的标注 prompt"""
    # preprocessed 包含预处理的关键点、mask 路径等辅助信息
    # 可以附加在 prompt 中帮助 LLM 做更准确的判断
    return ANNOTATION_PROMPT_TEMPLATE  # 见上文 Prompt 模板

@retry(stop=stop_after_attempt(MAX_RETRIES),
       wait=wait_exponential(multiplier=1, min=2, max=30))
def annotate_single(photo_path: str, preprocessed_path: str,
                    client: openai.OpenAI, model: str) -> dict:
    """对单张照片调用 Vision API 进行美学标注"""

    # 将照片转为 base64
    import base64
    with open(photo_path, "rb") as f:
        img_b64 = base64.b64encode(f.read()).decode()

    response = client.chat.completions.create(
        model=model,
        messages=[{
            "role": "user",
            "content": [
                {
                    "type": "image_url",
                    "image_url": {"url": f"data:image/jpeg;base64,{img_b64}"}
                },
                {
                    "type": "text",
                    "text": build_annotation_prompt(
                        json.load(open(preprocessed_path)))
                }
            ]
        }],
        max_tokens=800,
        temperature=0.1,   # 低温度保证输出一致性
        response_format={"type": "json_object"},  # GPT-4V 支持 JSON mode
    )

    raw = response.choices[0].message.content
    return json.loads(raw)

def validate_annotation(annot: dict) -> list[str]:
    """校验 LLM 输出是否符合 Schema, 返回错误列表"""
    errors = []
    # 必填字段检查
    required_paths = [
        "scene.category", "scene.is_indoor",
        "lighting.key_light_direction",
        "composition.rule_of_thirds_applied",
        "camera.angle", "camera.pitch_estimate_degrees",
        "camera.distance_to_subject",
        "subject.person_count", "subject.pose_type",
        "aesthetic_scores.overall",
    ]
    for path in required_paths:
        parts = path.split(".")
        val = annot
        for p in parts:
            val = val.get(p) if isinstance(val, dict) else None
        if val is None:
            errors.append(f"Missing: {path}")

    # 数值范围检查
    score = annot.get("aesthetic_scores", {}).get("overall", -1)
    if not (0 <= score <= 10):
        errors.append(f"Score out of range: {score}")

    pitch = annot.get("camera", {}).get("pitch_estimate_degrees", 999)
    if not (-90 <= pitch <= 90):
        errors.append(f"Pitch out of range: {pitch}")

    return errors

def batch_annotate(input_dir: str, output_dir: str,
                   api: str = "openai", model: str = "gpt-4o"):
    """
    批量标注主函数
    1. 加载所有预处理结果
    2. 过滤已完成标注的 (支持断点续传)
    3. 并发调用 LLM API
    4. 每批保存 checkpoint
    5. 最终生成汇总 JSON
    """
    os.makedirs(output_dir, exist_ok=True)

    # 加载待处理列表
    preprocessed_files = sorted(Path(input_dir).glob("*.json"))
    completed_ids = {f.stem for f in Path(output_dir).glob("*.json")
                     if f.stem != "summary"}
    pending = [f for f in preprocessed_files if f.stem not in completed_ids]

    print(f"Total: {len(preprocessed_files)}, "
          f"Completed: {len(completed_ids)}, "
          f"Pending: {len(pending)}")

    # 初始化 API client
    client = openai.OpenAI() if api == "openai" else None  # 或 Anthropic

    # 并发标注
    results = {}
    failed = []
    with ThreadPoolExecutor(max_workers=CONCURRENCY) as executor:
        futures = {
            executor.submit(
                annotate_single,
                photo_path=str(f).replace(".json", ".jpg"),
                preprocessed_path=str(f),
                client=client,
                model=model,
            ): f.stem
            for f in pending
        }

        for i, future in enumerate(as_completed(futures)):
            photo_id = futures[future]
            try:
                annotation = future.result()
                errors = validate_annotation(annotation)
                if errors:
                    print(f"[WARN] {photo_id}: {errors}")
                    failed.append({"id": photo_id, "errors": errors})

                # 合并预处理数据 + LLM 标注 → 完整模板
                pre = json.load(open(f"{input_dir}/{photo_id}.json"))
                template = {**pre, "aesthetic_annotation": annotation}
                template["keypoints_normalized"] = normalize_keypoints(
                    pre["keypoints_abs"], pre["width"], pre["height"])

                with open(f"{output_dir}/{photo_id}.json", "w") as f:
                    json.dump(template, f, ensure_ascii=False, indent=2)

                results[photo_id] = template

            except Exception as e:
                print(f"[ERROR] {photo_id}: {e}")
                failed.append({"id": photo_id, "error": str(e)})

            # 进度 & checkpoint
            if (i + 1) % SAVE_INTERVAL == 0:
                print(f"Progress: {i+1}/{len(pending)}, "
                      f"Success: {len(results)}, Failed: {len(failed)}")
                save_checkpoint(results, failed, output_dir)

    # 最终汇总
    save_checkpoint(results, failed, output_dir)
    print(f"\nDone. Annotated: {len(results)}, Failed: {len(failed)}")
    return results, failed
```

#### 6.3.4 质量校验三步法

```
第一步: Schema 校验 (程序自动)
  ├── JSON 格式正确性
  ├── 必填字段完整性
  ├── 数值范围合理性
  └── 枚举值合法性
  → 不通过的照片进入 failed 队列, 换更强模型重试

第二步: 一致性校验 (程序自动)
  ├── 同场景类别内 embedding 余弦相似度分布检查
  ├── 标注结果与预处理关键点的一致性 (如标注说 "standing" 但关键点显示坐姿)
  └── aesthetic_scores 分布检查 (避免全 8-9 分, 需要有区分度)
  → 标记异常样本, 人工复核

第三步: 人工抽检 (200 张)
  ├── 每种场景类别抽 20 张
  ├── 检查构图分析的准确性
  ├── 检查相机角度估计的合理性
  └── 检查姿势描述的精确性
  → 抽检通过率 > 90% 视为合格, 否则扩大人工复核范围
```

### 6.5 USearch 向量索引构建

```python
# tools/build_template_db/build_index.py

from usearch.index import Index
import numpy as np

def build_usearch_index(templates_dir: str, output_path: str):
    """
    从已标注的模板 JSON 文件构建 USearch 向量索引

    输出:
      - templates.idx: USearch 二进制索引文件
      - templates_meta.bin: 模板元数据 (JSONL 格式, 与索引同序)
    """

    templates = []
    for f in sorted(Path(templates_dir).glob("*.json")):
        t = json.load(open(f))
        templates.append(t)

    # 提取所有 embedding (256d)
    embeddings = np.array([t["scene_embedding"] for t in templates],
                          dtype=np.float32)

    # 构建 USearch 索引
    dim = embeddings.shape[1]  # 256
    index = Index(ndim=dim, metric="cos", dtype="f32")

    # 批量插入 (带 ID)
    ids = np.arange(len(templates), dtype=np.int64)
    index.add(ids, embeddings)

    # 保存索引
    index.save(f"{output_path}/templates.idx")

    # 保存元数据 (JSONL 格式, 行号 = 索引 ID)
    with open(f"{output_path}/templates_meta.jsonl", "w") as f:
        for t in templates:
            # 去除 embedding (已在索引中), 保留其余数据
            meta = {k: v for k, v in t.items() if k != "scene_embedding"}
            f.write(json.dumps(meta, ensure_ascii=False) + "\n")

    print(f"Index built: {len(templates)} templates, "
          f"dim={dim}, index_size={os.path.getsize(f'{output_path}/templates.idx')/1024:.1f}KB")

    # 验证: 自检索检查
    test_vec = embeddings[0]
    results = index.search(test_vec, 3)  # top-3
    assert results[0].keys[0] == 0, "Self-retrieval failed!"
    print("Self-retrieval check passed.")
```

## 七、核心工程痛点与解决方案

### 7.1 痛点一：视觉无关特征剥离（条件执行）

**问题**: 在**人像场景**中，CLIP 向量检索时人物的服装颜色、穿搭风格会严重干扰场景匹配。但在**风景和静物场景**中不存在此问题——画面中没有人物，整帧都是有效信息。

**方案**: 条件特征解耦 (Conditional Feature Isolation)

```
输入帧
  │
  ├──► YOLOv8-Pose 检测 ──► 是否有人？
  │         │
  │    ┌────┴────┐
  │    │ 有人     │ 无人
  │    ▼         ▼
  │  人像路径    风景/静物路径
  │    │         │
  │    ├─ MediaPipe Seg      ├─ 跳过分割
  │    ├─ 人像区域置黑        ├─ 全帧保留
  │    └─ CLIP(背景图)       └─ CLIP(全帧)
  │         │                     │
  │         └──────┬──────────────┘
  │                ▼
  │         256d Embedding → USearch 检索
```

**实现细节**:
- 先跑 YOLOv8-Pose（内圈本就需要的），根据是否检测到人（置信度 > 0.5 的关键点 ≥ 5 个）来决定路径
- **有人**：MediaPipe 分割 → 人像置黑 → CLIP 提取纯背景向量（避免服装干扰场景匹配）
- **无人**：跳过分割，全帧直接送 CLIP（风景/静物的所有像素都是有效信息）
- 人像遮罩操作在 YUV 色彩空间直接执行（避免 YUV→RGB→YUV 转换开销）
- 仅在"外圈触发"时执行（场景切换检测），不对每帧执行节省算力

### 7.2 痛点二：肢体形变归一化（仅人像场景）

**问题**: 不同身高、体重、身材比例的人，绝对像素坐标的骨骼关键点无法直接比对。一个 160cm 和一个 190cm 的人做同一个姿势，像素坐标完全不同。

**适用条件**: 仅当画面中检测到人物时启用。风景和静物场景跳过此模块。

**方案**: Root-centered Scaling + 关节夹角比对

```
实时关键点 (绝对像素坐标)              模板关键点 (绝对像素坐标)
        │                                       │
        ├── 计算基准长度 L = dist(左肩, 右髋)     ├── 同样计算 L_template
        │                                       │
        ├── 所有坐标 ÷ L (空间归一化)             ├── 所有坐标 ÷ L_template
        │                                       │
        └────────── 归一化坐标可直接比对 ──────────┘
                          │
              ┌───────────┴───────────┐
              │                       │
        位置差值 (归一化空间)      夹角差值 (度)
        Δx, Δy per joint          Δθ per joint
              │                       │
              └───────────┬───────────┘
                          │
                    综合得分 + 引导方向
```

**关节夹角计算**（C++ 实现）:

```cpp
// 计算三点夹角 (度)
float joint_angle(Point a, Point b, Point c) {
    // 以 b 为顶点的夹角: ∠ABC
    float dx1 = a.x - b.x, dy1 = a.y - b.y;
    float dx2 = c.x - b.x, dy2 = c.y - b.y;
    float dot = dx1*dx2 + dy1*dy2;
    float cross = dx1*dy2 - dy1*dx2;
    float angle_rad = std::atan2(std::abs(cross), dot);
    return angle_rad * 180.0f / M_PI;
}

// 计算所有关键关节夹角
JointAngles compute_joint_angles(const Keypoint* kpts) {
    return {
        .left_elbow    = joint_angle(kpts[5], kpts[7], kpts[9]),   // 左肩-肘-腕
        .right_elbow   = joint_angle(kpts[6], kpts[8], kpts[10]),
        .left_knee     = joint_angle(kpts[11], kpts[13], kpts[15]),
        .right_knee    = joint_angle(kpts[12], kpts[14], kpts[16]),
        .left_shoulder = joint_angle(kpts[7], kpts[5], kpts[11]),  // 肘-肩-髋
        .right_shoulder= joint_angle(kpts[8], kpts[6], kpts[12]),
        .spine_tilt    = spine_angle(kpts[5], kpts[6], kpts[11], kpts[12]),
        .head_tilt     = head_angle(kpts[0], kpts[5], kpts[6]),
    };
}
```

**容差设定**: ±10° 为"对齐"阈值，±10°~±20° 为"接近"，大于 ±20° 触发姿势引导箭头。

### 7.3 痛点三：语义翻译层

**问题**: 底层算出的多维物理差值（Δpitch=-12°, Δleft_elbow=-25°, Δhorizon=0.15...）对用户毫无意义，需要转化为通俗自然的语言。

**方案**: 两级翻译管线

```
底层 Δ 数据 (多维浮点向量)
        │
        ▼
┌───────────────────────────────────────────┐
│ 第一级: 规则引擎 (C++, 每帧, <0.1ms)       │
│                                            │
│ 将数值差值映射为"语义槽位"                   │
│ 例: Δpitch = -12° → slot:camera="抬高一点"  │
│     Δleft_elbow = -25° → slot:pose="左臂弯多些" │
│                                            │
│ 输出: Structured Suggestion JSON            │
└───────────────────┬───────────────────────┘
                    │
                    ▼
┌───────────────────────────────────────────┐
│ 第二级: LLM 融合 (SmolLM2-360M, 300-500ms)│
│                                            │
│ 将多个语义槽位融合为自然语句                 │
│ Prompt 模板:                                │
│ "将以下摄影建议融合为一句话(≤30字,口语化):    │
│  [相机: 抬高一点, 左移半步]                  │
│  [姿势: 左臂弯曲约25度, 头稍向左转]          │
│  [构图: 人物放在画面右边1/3处]               │
│  输出自然的中文建议:"                        │
│                                            │
│ → "往右挪半步，相机抬高一点，左手臂再弯一些"   │
└───────────────────────────────────────────┘
```

### 阶段 4：差值计算与规则引擎（3 周）

**目标**: 实现精确的 Δ 求解和第一级语义映射。

| 输入 | 输出 | 工具/框架 |
|---|---|---|
| 实时关键点 + TargetVector | Δ 数据 + Structured Suggestions JSON | C++17, Eigen |

**详细步骤**:

1. **骨骼归一化模块** (Week 1)
   - Root-centered Scaling 实现（见 7.2）
   - 关节夹角计算（见 7.2）
   - 文件: `engine/src/core/skeleton_normalizer.cpp`

2. **多维差值求解器** (Week 1-2)
   - `engine/src/core/delta_solver.cpp`
   - 骨骼差值: 每个关节夹角与模板夹角的 Δθ
   - 相机差值: 当前 IMU 角度 vs 模板建议角度
   - 构图差值: 当前主体位置 vs 模板三分线位置
   - 曝光差值: 当前画面平均亮度 vs 模板亮度
   - 输出统一 `DeltaSnapshot` 结构

3. **目标点与姿势箭头生成器** (Week 2)
   - `engine/src/core/camera_target_generator.cpp` — 相机目标点
   - `engine/src/core/pose_arrow_generator.cpp` — 姿势箭头
   - 目标点逻辑：
     ```
     模板建议 subject_placement = (0.33, 0.5)
     → 目标点位置 = 模板构图中心
     → offset_magnitude = |目标点 - 画面中心|
     → 用户移动相机使 center → target_point
     ```
   - 姿势箭头逻辑：
     ```
     if |Δpose.left_elbow| > 10°:
         → 在左肘位置生成姿势调整箭头
     ```

4. **规则引擎（第一级语义映射）** (Week 2-3)
   - `engine/src/core/rule_engine.cpp`
   - 将 Δ 数值映射为语义槽位，例如：
     ```cpp
     struct SemanticSlots {
         std::string camera_action;    // "抬高一点" / "放低一点" / ""
         std::string move_action;      // "往左走半步" / "往右一步" / ""
         std::string pose_action;      // "左臂弯一些" / "头向右转" / ""
         std::string framing_action;   // "人物放画面右边" / ""
     };
     ```
   - 映射规则表（可配置 JSON）：
     ```json
     {
       "camera_pitch": [
         {"range": [-90, -15], "slot": "相机抬高"},
         {"range": [-5, 5], "slot": ""},
         {"range": [5, 90], "slot": "相机放低"}
       ]
     }
     ```

**验收标准**:
- [ ] 给定一张照片和其模板，差值求解器输出的 Δ 经人工验证合理
- [ ] 规则引擎输出的语义槽位与实际物理直觉一致
- [ ] 箭头生成逻辑覆盖平移、旋转、俯仰三种类型

**渲染层技术方案（供 App 团队参考）**:

```kotlin
// GuidanceOverlayView.kt — 自定义 View 绘制引导叠加层

class GuidanceOverlayView(context: Context) : View(context) {
    private var currentGuidance: GuidanceOutput? = null

    // 画笔
    private val arrowPaint = Paint().apply { /* ... */ }
    private val posePaint = Paint().apply { /* ... */ }
    private val compPaint = Paint().apply { /* ... */ }
    private val textPaint = Paint().apply { /* ... */ }

    fun updateGuidance(g: GuidanceOutput) {
        currentGuidance = g
        invalidate()  // 触发 onDraw
    }

    override fun onDraw(canvas: Canvas) {
        super.onDraw(canvas)
        val w = width.toFloat()
        val h = height.toFloat()
        val g = currentGuidance ?: return

        // 1. 绘制构图辅助线 (最底层)
        drawCompGuides(canvas, g.composition, w, h)

        // 2. 绘制虚线人形 (中间层, 仅人像)
        if (g.pose.has_person) drawPoseOverlay(canvas, g.pose, w, h)

        // 3. 绘制姿势引导箭头 (人像时在关节位置)
        drawPoseArrows(canvas, g.pose_arrows, g.pose_arrow_count, w, h)

        // 4. 绘制相机目标点 (最上层, 始终显示)
        drawCameraTarget(canvas, g.camera_target, w, h)

        // 5. 绘制文本建议 (底部)
        drawTextSuggestion(canvas, g.text, w, h)
    }
}
```

**优化手段**:

1. **CPU/GPU 优化**
   - NEON SIMD 手写关键循环（YUV→RGB, 归一化）
   - TFLite GPU Delegate: 尝试将多个小模型合并为一个推理图减少 dispatch 开销
   - 算子融合: YOLOv8 NMS 用 GPU 实现

2. **内存优化**
   - 帧缓冲区池化 (Object Pool): 预分配 6 个 YUV Buffer, 循环使用
   - 模型权重的 mmap 加载: 多进程共享同一物理页
   - 中间张量复用: TFLite 推理间共享 tensor arena

3. **散热管理**
   - 设备温度监控 (`PowerManager.THERMAL_STATUS_*`)
   - 热状态分级降档:
     ```
     THERMAL_STATUS_NONE     → 标准模式, LLM 每 1s
     THERMAL_STATUS_LIGHT    → 标准模式, LLM 每 2s
     THERMAL_STATUS_MODERATE → 轻量模式, LLM 每 3s
     THERMAL_STATUS_SEVERE   → 极简模式, 无 LLM, 15fps
     ```
